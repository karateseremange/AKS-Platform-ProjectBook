## 1. Objet

Ce document détaille le lot C prévu par ADMIN-006-02 après l’intégration des lots A et B. Il cadre le client serveur du portail RECETTE et l’isolation fonctionnelle du widget Journaux.

Le résultat attendu est qu’un utilisateur autorisé puisse ouvrir Administration même si le service Journaux est absent, désactivé ou en erreur. Le présent cadrage ne modifie aucun code, projet Apps Script, secret, support Google, habilitation ou déploiement.

## 2. Décision fonctionnelle

Paramétrage et Journaux restent deux modules fonctionnels distincts :

- Paramétrage dépend exclusivement des capacités `CONFIG_READ`, `CONFIG_WRITE` et `CONFIG_RESET` ;
- Journaux dépend exclusivement de `LOG_READ` ;
- l’échec de Journaux ne modifie ni la visibilité ni le fonctionnement de Paramétrage ;
- l’échec de Paramétrage ne modifie ni la visibilité ni le fonctionnement de Journaux ;
- la carte Administration peut regrouper visuellement les destinations, mais chaque destination conserve son autorisation, son chargement et son état propres.

Le lot C ne traite que Journaux. Il ne raccorde aucune capacité `CONFIG_*`.

## 4. Architecture logique

| Composant | Responsabilité | État initial |
|---|---|---|
| Projection du portail | exposer Journaux seulement avec `LOG_READ` | existante, à préserver |
| Service Journaux du portail | contrôler l’acteur, construire la commande et interpréter la réponse | à implémenter |
| Fabrique de requêtes lot A | canonicalisation, empreinte et signature | intégrée |
| Port de transport privé | envoyer le corps et recevoir la réponse brute | injecté, inactif |
| Backend lot B | vérifier, consommer et lire LOG | intégré, inactif |
| Contrôleur Administration | isoler l’état Journaux du rendu global | à adapter |
| Vue Journaux | présenter les événements ou un état contrôlé | à adapter |

Le navigateur ne construit jamais l’enveloppe signée, ne connaît pas le secret, ne reçoit pas l’URL interne et n’appelle pas directement le backend.

## 5. Séquence serveur future

Pour une lecture Journaux autorisée :

1. recevoir une action utilisateur ou une demande de widget ;
2. résoudre l’utilisateur actif côté serveur ;
3. normaliser l’adresse ;
4. vérifier le compte actif et la capacité `LOG_READ` ;
5. vérifier que le raccordement privé RECETTE est explicitement actif ;
6. générer `requestId`, `correlationId`, nonce et fenêtre temporelle ;
7. construire et signer `LOG_READ_RECENT_V1` côté serveur ;
8. appeler le port de transport injecté avec une URL configurée côté serveur ;
9. appliquer un délai et une taille de réponse bornés ;
10. décoder le JSON ;
11. vérifier signature, environnement et corrélation ;
12. projeter uniquement les champs autorisés ;
13. retourner un résultat fonctionnel au contrôleur ;
14. transformer tout échec en état Journaux isolé.

Aucun appel réseau ne doit avoir lieu avant le contrôle ACCESS.

## 6. Autorisation et identité

### 6.1 Source d’identité

L’acteur provient exclusivement de l’identité serveur résolue par le portail. Une adresse issue du navigateur ou du payload utilisateur est interdite.

Une identité vide, non normalisable ou incohérente produit `PRIVATE_AUTH_REQUIRED`.

### 6.2 Source d’autorisation

Le service exige explicitement `LOG_READ` sur le compte actif. Un rôle descriptif, y compris `ADMINISTRATEUR`, ne remplace pas cette capacité.

Le refus intervient avant :

- la lecture de la configuration privée ;
- la génération d’une signature ;
- l’appel du transport ;
- toute tentative de lecture LOG.

### 6.3 Retrait du droit

Après retrait de `LOG_READ` :

- la destination Journaux disparaît de la projection ;
- un appel direct serveur est refusé ;
- aucune réponse antérieure ne doit être réutilisée comme autorisation ;
- Paramétrage et les autres modules restent inchangés.

## 7. Configuration future

Les valeurs suivantes resteront exclusivement côté serveur :

| Propriété logique | Usage |
|---|---|
| `AKS_PRIVATE_PORTAL_ENABLED` | coupe-circuit du client |
| `AKS_PRIVATE_PORTAL_ENVIRONMENT` | valeur exacte `RECETTE` |
| `AKS_PRIVATE_BACKEND_URL` | endpoint autorisé |
| `AKS_PRIVATE_CALLER_PROJECT` | identifiant logique du portail |
| `AKS_PRIVATE_HMAC_CURRENT` | secret courant |
| `AKS_PRIVATE_HMAC_PREVIOUS` | secret précédent durant rotation |
| `AKS_PRIVATE_TIMEOUT_MS` | délai borné |

Aucune valeur réelle n’est inscrite dans Git ou le Project Book. L’absence ou l’incohérence d’une propriété maintient Journaux indisponible sans bloquer Administration.

## 8. Port de transport

Le lot C doit définir une interface pure, par exemple :

`transport.send(rawBody, context)`

Le contexte contient uniquement des valeurs techniques bornées, jamais le secret. L’adaptateur réel futur :

- utilise une URL serveur configurée ;
- accepte uniquement HTTPS ;
- effectue un `POST` JSON ;
- désactive les redirections non prévues ;
- applique un délai borné selon les possibilités Apps Script ;
- limite le corps de réponse ;
- n’enregistre ni requête signée complète, ni réponse brute ;
- convertit les statuts et exceptions en `PRIVATE_BACKEND_UNAVAILABLE`.

L’adaptateur livré par le lot C reste inactif tant que le raccordement n’est pas explicitement autorisé.

## 9. Construction de la requête

Le service réutilise `AKS_createPrivateProtocol_` du lot A et ne duplique pas la canonicalisation.

Valeurs proposées :

- commande : `LOG_READ_RECENT_V1` ;
- fenêtre : 60 secondes maximum ;
- nonce : au moins 128 bits via générateur injecté ;
- `requestId` et `correlationId` uniques ;
- limite par défaut : 5 ;
- limite maximale : 20 ;
- sévérité et curseur validés par le contrat existant.

Le secret est lu au dernier moment côté serveur et n’est jamais renvoyé par le service.

## 10. Validation de la réponse

Avant toute projection UI, le client vérifie :

- protocole `AKS-PRIVATE/1` ;
- environnement `RECETTE` ;
- `requestId` ;
- `correlationId` ;
- empreinte des données ;
- signature HMAC ;
- statut fermé `OK` ou `ERROR` ;
- schéma et taille des événements ;
- curseur borné.

Une réponse invalide, altérée, non corrélée ou surdimensionnée devient `PRIVATE_BACKEND_UNAVAILABLE`. Aucun contenu partiel n’est affiché.

## 11. Isolation du widget Journaux

### 11.1 Suppression du chargement bloquant

La construction initiale de la page Administration ne doit plus exiger la lecture des cinq événements récents pour réussir.

Deux modes sont acceptables :

- chargement paresseux après affichage de la page ;
- chargement serveur isolé dont l’échec est capturé dans un modèle Journaux local.

Dans les deux cas, la route `?app=admin` reste utilisable.

### 11.2 États du widget

| État | Présentation | Navigation globale |
|---|---|---|
| non autorisé | destination absente ou refus neutre | disponible |
| désactivé | message « Journaux temporairement indisponibles » | disponible |
| chargement | indicateur local | disponible |
| disponible | événements minimisés | disponible |
| erreur technique | message générique et action Réessayer | disponible |
| vide | message « Aucun événement disponible » | disponible |

Aucune pile, URL, identité technique, propriété ou identifiant Google n’est affiché.

### 11.3 Réessai

Le bouton Réessayer génère une nouvelle requête avec de nouveaux identifiants et nonce. Il ne rejoue jamais l’enveloppe précédente.

Une limitation locale évite les doubles clics et les appels concurrents inutiles.

## 12. Contrat du service portail

Le service retourne un résultat fermé :

```json
{
  "status": "AVAILABLE",
  "events": [],
  "nextCursor": null,
  "correlationId": "correlation-technique"
}
```

Statuts autorisés :

- `AVAILABLE` ;
- `EMPTY` ;
- `DISABLED` ;
- `UNAVAILABLE`.

Les codes de sécurité internes ne sont pas transmis tels quels au navigateur. Le contrôleur décide uniquement du modèle visuel local.

## 13. Séparation Paramétrage / Journaux

Les règles suivantes sont obligatoires :

- `CONFIG_READ` seul n’expose pas Journaux ;
- `LOG_READ` seul n’expose pas Paramétrage ;
- `CONFIG_WRITE` ou `CONFIG_RESET` ne déclenche aucun appel LOG ;
- l’indisponibilité LOG ne retire pas la carte ou les actions Paramétrage ;
- la navigation rapide contient deux actions distinctes lorsqu’elles sont autorisées ;
- la fiche d’habilitation peut regrouper les capacités dans un encart Administration, mais les octrois restent indépendants.

Cette séparation doit être couverte par des tests de projection et de rendu.

## 14. Gestion des erreurs

| Situation interne | Résultat du service | Effet sur Administration |
|---|---|---|
| identité absente | refus serveur | page accessible selon les autres droits |
| `LOG_READ` absent | refus avant transport | aucune destination Journaux |
| client désactivé | `DISABLED` | widget local indisponible |
| configuration absente | `UNAVAILABLE` | widget local indisponible |
| délai ou réseau | `UNAVAILABLE` | widget local indisponible |
| réponse altérée | `UNAVAILABLE` | aucun contenu affiché |
| backend refuse | `UNAVAILABLE` | réessai possible selon politique |
| événements vides | `EMPTY` | page normale |

Le portail ne doit pas distinguer visuellement une mauvaise signature d’un backend indisponible.
