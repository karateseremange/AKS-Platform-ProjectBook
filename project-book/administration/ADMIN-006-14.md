## 3. Décision d’identité d’exécution

Le backend doit s’exécuter sous l’identité du compte qui réalise son déploiement, soit `USER_DEPLOYING`.

En RECETTE, le déploiement doit être réalisé exclusivement par le propriétaire observé `karate.seremange@gmail.com`, qui possède déjà le projet backend, le support LOG et le support de preuve. Aucun partage utilisateur supplémentaire n’est requis.

Cette décision :

- isole les permissions Google des comptes qui utilisent le portail ;

- ne crée pas de compte technique distinct ;
- ne vaut pas décision d’identité pour la PRODUCTION ;
- impose de contrôler à nouveau le propriétaire avant le déploiement.

## 4. Décision d’audience

Le portail appelle le backend côté serveur par `UrlFetchApp` sans cookie de session Google ni jeton OAuth transmis. L’audience compatible est donc `ANYONE_ANONYMOUS`.

Le manifeste cible devra contenir :

```json
"webapp": {
  "access": "ANYONE_ANONYMOUS",
  "executeAs": "USER_DEPLOYING"
}
```

Selon la documentation Apps Script, `ANYONE_ANONYMOUS` autorise l’invocation sans connexion Google et `USER_DEPLOYING` exécute la Web App sous l’identité du déployeur. Cette audience augmente la surface réseau ; elle n’est admissible que parce que le backend applique cumulativement :

- commande unique `LOG_READ_RECENT_V1` ;
- protocole exact `AKS-PRIVATE/1` ;
- HMAC ;
- fenêtre temporelle ;
- projet appelant et environnement exacts ;
- `requestId` et nonce uniques ;
- registre anti-rejeu ;
- corps et résultat bornés ;
- réponses d’erreur génériques ;
- absence de secret et d’URL dans les journaux ;
- backend désactivé par défaut.

Références officielles :

- https://developers.google.com/apps-script/manifest/web-app-api-executable
- https://developers.google.com/apps-script/guides/web

## 5. Modification applicative préalable obligatoire

Le manifeste D3-A validé ne contient volontairement aucune section `webapp`. Le déploiement ne doit pas utiliser une modification locale non revue.

D3-D est donc découpé en quatre sous-lots. Le premier est obligatoirement applicatif.

Aucune opération Google n’est incluse.

### D3-D2 — validation réversible du manifeste

Aucune version ni aucun déploiement n’est créé.

## 6. Précontrôles fermés

Chaque sous-lot s’arrête avant mutation si :

- la référence applicative attendue a changé ;
- le HEAD backend n’est pas celui attendu ;
- les onze propriétés ne sont pas exactes ;
- le secret ou sa version a changé ;
- `AKS_PRIVATE_HMAC_PREVIOUS` est présente ;
- `AKS_PRIVATE_ENABLED` n’est pas `false` au départ ;
- un support est partagé à un compte utilisateur ;
- le schéma LOG ou preuve a changé ;
- une version ou un déploiement backend existe avant D3-D3 ;
- le propriétaire ou le compte déployeur n’est pas celui attendu ;
- le manifeste contient une autre audience ou identité ;
- le package ne contient pas exactement sept fichiers ;
- le portail contient déjà une URL backend ou un transport actif.

## 7. Tests de refus avant activation

Le déploiement inactif doit retourner une erreur générique pour :

- GET ou absence de POST valide ;
- corps vide ;
- JSON invalide ;
- protocole ou commande inconnus ;
- signature absente, invalide ou altérée ;
- environnement ou projet appelant incorrect ;
- requête expirée ou située dans le futur ;
- identifiants absents ou mal formés ;
- corps trop volumineux.

Aucun test de refus ne doit :

- ouvrir le support LOG ;
- écrire une preuve ;
- créer une clé anti-rejeu ;
- afficher la signature, le secret ou l’URL dans un rapport public ;
- modifier le portail.

## 8. Test signé contrôlé

Le test signé ne peut avoir lieu qu’après D3-D3 et sous autorisation D3-D4. Il utilise le secret déjà installé dans les propriétés du portail sans l’extraire ni l’afficher.

La preuve attendue est exactement une nouvelle ligne comprenant le hash de l’acteur et les identifiants techniques, jamais son adresse en clair. Le support LOG reste en lecture seule.

Le test est conforme uniquement si :

- la première requête réussit ;
- au plus vingt événements minimisés sont retournés ;
- une seule preuve est écrite puis relue ;
- le rejeu exact est refusé ;
- aucune seconde preuve de succès n’est créée ;
- aucune donnée LOG n’est modifiée ;
- aucun support n’est partagé ;
- le backend est remis à `false` immédiatement après le test.

Restaurer le HEAD. La version Apps Script immuable reste consignée comme version non déployée. Aucune tentative de suppression ou de réécriture n’est autorisée.

### 14.4 Incident de préparation et corrections

La première révision s'est arrêtée au précontrôle PowerShell sur un appel positionnel erroné à `Get-FileHash` : l'algorithme doit être fourni avec `-Algorithm SHA256`. Dans l'ordre du script concerné, cet arrêt précède les push temporaires et l'activation.

La relecture a également identifié un nettoyage par préfixe trop large, susceptible d'englober les paramètres de configuration anti-rejeu, et une suppression globale des propriétés utilisateur. Ces défauts ont été corrigés avant la nouvelle exécution. La révision 2 :

- utilise les paramètres PowerShell explicites ;
- ne supprime que les deux clés anti-rejeu calculées pour son propre run ;
- préserve les propriétés utilisateur sans rapport avec l'opération ;
- fournit un protocole de signature isolé au harnais portail ;
- relit les deux projets instrumentés avant activation ;
- conserve les fonctions de secours lorsque la restauration reste incertaine.

Vingt-cinq tests locaux simulés ont été annoncés réussis lors de la préparation de cette révision. Ils sont distincts du test réel D3-D4 et ne constituent pas une nouvelle exécution de la suite cumulative Apps Script.

Aucune version, aucun déploiement, aucun partage, aucune attribution ACCESS et aucune opération de production n'ont été effectués par cette campagne selon le résultat transmis. Les propriétés et le code ont, eux, été modifiés temporairement puis restaurés ; la preuve de succès a été écrite et conservée.
