## 1. Objet

Ce document cadre le premier raccordement réel de l’architecture privée conçue dans les lots A à C. Il définit les ressources à inventorier, les identités, les droits minimaux, le secret HMAC, le registre anti-rejeu, les preuves, la recette multi-compte et le retour arrière.

Il ne choisit, ne crée et ne modifie aucune ressource Google. Il n’autorise ni secret, ni déploiement, ni partage, ni habilitation ACCESS.

## 2. État de départ historique

État initial conservé pour traçabilité ; l'état courant est au §20. Les éléments suivants étaient intégrés dans `develop` :

- protocole signé `AKS-PRIVATE/1` ;
- commande fermée `LOG_READ_RECENT_V1` ;
- backend privé, adaptateurs et registre anti-rejeu inactifs ;
- client portail contrôlant `LOG_READ` avant tout transport ;
- widget Journaux isolé avec fonctionnement dégradé ;
- 716 tests cumulatifs réussis en RECETTE ;
- restauration exacte du HEAD RECETTE après validation.

Le portail RECETTE connu porte un identifiant Apps Script suffixé `eIRxs4`. Aucun projet backend, endpoint, secret ou support LOG n’est désigné par le présent document.

## 3. Objectif fonctionnel

Un compte secondaire disposant de `LOG_READ` doit pouvoir :

1. ouvrir le portail RECETTE sous sa propre identité ;
2. voir la destination Journaux sans acquérir de capacité `CONFIG_*` ;
3. déclencher une lecture signée côté serveur ;
4. recevoir uniquement des événements minimisés ;
5. conserver l’accès au reste du portail si le backend est indisponible.

Après retrait de `LOG_READ`, la destination doit disparaître et tout appel direct doit être refusé avant transport.

## 7. Identités et droits minimaux

### 7.1 Utilisateur du portail

L’adresse est résolue côté serveur par le portail. Elle n’est jamais acceptée depuis le navigateur.

L’utilisateur reçoit seulement les capacités fonctionnelles nécessaires. `LOG_READ` ne confère ni `CONFIG_READ`, ni `CONFIG_WRITE`, ni `CONFIG_RESET`, ni `ACCESS_MANAGE`.

### 7.2 Identité technique backend

Exigences cibles initiales. La décision RECETTE ultérieure d'ADMIN-006-14 §3 utilise le propriétaire existant, sans compte technique distinct ; ces exigences ne constituent pas une attestation de ses droits réels.

L’identité technique doit :

- être distincte des comptes de test utilisateur ;
- avoir uniquement la lecture du support LOG RECETTE ;
- avoir uniquement l’écriture minimale du support de preuve retenu ;
- ne disposer d’aucun accès aux supports PRODUCTION ;
- ne pas être utilisée pour naviguer dans le portail ;
- être inventoriée avant tout partage.

### 7.3 Opérateur

L’opérateur autorisant le raccordement doit être vérifié séparément. Son rôle ne doit pas être confondu avec l’identité technique d’exécution.

## 8. Déploiement privé

Le backend doit résider dans un projet distinct du portail `USER_ACCESSING`.

Avant création d’un déploiement, le protocole doit fixer :

- l’identité d’exécution ;
- l’audience minimale techniquement viable ;
- la version exacte ;
- la description de version ;
- l’URL attendue ;
- le mécanisme d’authentification applicative HMAC ;
- l’absence de route autre que la commande fermée ;
- la procédure de suppression ou de désactivation.

Une audience réseau large ne vaut jamais autorisation fonctionnelle. Toute requête reste refusée sans signature, environnement, projet appelant, fenêtre temporelle et anti-rejeu valides.

## 9. Secret HMAC

### 9.1 Génération

Le secret doit :

- être généré par une source cryptographique ;
- contenir au moins 256 bits d’entropie ;
- ne jamais transiter dans le chat, Git, un rapport ou une cellule ;
- être installé directement dans les propriétés serveur autorisées ;
- être référencé par empreinte uniquement dans les preuves.

### 9.2 Stockage

Les propriétés logiques sont :

- `AKS_PRIVATE_HMAC_CURRENT` ;
- `AKS_PRIVATE_HMAC_PREVIOUS` pendant une rotation bornée ;
- `AKS_PRIVATE_SECRET_VERSION`.

Le portail et le backend doivent recevoir la même version courante. Toute divergence maintient Journaux indisponible sans bloquer Administration.

### 9.3 Rotation

La rotation suit quatre phases :

1. installer le nouveau secret comme courant côté backend et conserver l’ancien ;
2. installer le nouveau secret côté portail ;
3. vérifier le nouveau flux ;
4. supprimer l’ancien secret des deux côtés après la fenêtre autorisée.

Un retour arrière doit être possible tant que l’ancien secret est conservé. Les valeurs ne sont jamais affichées.

### 20.3 Contrat fonctionnel et sécurité

Widget : cinq événements récents ; page Journaux RECETTE : vingt maximum et filtre de sévérité. Pas de pagination, recherche libre, catégorie ou export dans ce prototype. Ne pas présenter cette vue comme l'équivalent complet des filtres historiques.

La recherche porte sur au plus les 500 dernières lignes de données du journal, hors en-tête, selon leur position dans la feuille. Le backend sélectionne d'abord cette fenêtre, applique ensuite le filtre de sévérité éventuel, puis limite les résultats aux cinq événements du widget ou aux vingt événements maximum de la page, en parcourant les lignes de la plus récente à la plus ancienne. Il n'explore pas les lignes antérieures à cette fenêtre pour compléter les résultats. Cette consultation ne garantit donc aucune exhaustivité historique ; un résultat vide ne démontre pas l'absence d'événements correspondants plus anciens.

L'interface doit afficher la limite à proximité des résultats, y compris lorsqu'ils sont vides : « Consultation limitée aux 500 dernières lignes du journal ; historique non exhaustif. » En cas de résultat vide, afficher « Aucun événement correspondant dans la fenêtre consultée (au plus 500 dernières lignes). » Ne pas présenter cet état comme l'absence d'événements dans tout le journal.

Cette précision décrit le comportement du backend au commit applicatif indiqué au §20.1. Elle ne modifie ni le backend, ni l'architecture, ni la validation technique D3-D4.

DTO fermé : date, sévérité, code, message borné, corrélation. Affichage texte échappé, sans actor/context. Un message peut néanmoins contenir des données personnelles : utiliser des événements synthétiques pour la preuve initiale.

Chaque RPC et chaque réessai contrôle LOG_READ côté serveur avant lecture du secret, signature et transport. Identité vide ou ACCESS indisponible : refus fermé. Ne jamais accepter acteur, projet, endpoint, secret ou support depuis le navigateur. Tester explicitement les exceptions bootstrap, sans les assimiler à une habilitation attribuée.

Aucun repli vers le dépôt LOG Google direct dans le chemin privé RECETTE, même en cas d'erreur ou de désactivation. Préserver les comportements hors RECETTE. CONFIG reste hors prototype ; LOG_READ ne confère aucune capacité CONFIG ou ACCESS_MANAGE.

Propriétés portail proposées selon [ADMIN-006-06](ADMIN-006-06.md) :

| AKS_PRIVATE_HMAC_PREVIOUS | Reste absente ; rotation exclue |
| AKS_PRIVATE_TIMEOUT_MS | Budget logique proposé 10 000 ms, pas un timeout natif UrlFetchApp |

Comparer le Script ID réel à la cible RECETTE complète approuvée ; ni suffixe seul ni environnement autodéclaré ne suffisent. Aucun I/O au chargement. Ne pas installer les clés PORTAL dans le backend, dont la configuration est fermée.

Réutiliser AKS-PRIVATE/1 et la validation des réponses signées : environnement, requestId, correlationId, empreinte et HMAC. POST HTTPS JSON vers l'endpoint exact, certificat validé, sans cookie ou jeton OAuth utilisateur. Tester explicitement les redirections ContentService : récupération GET de réponse vers destination Google strictement contrôlée, sans retransmettre le corps signé à une autre origine. Refuser les destinations arbitraires.

Corps signé au plus 16 Kio, réponse au plus 32 Kio avant parsing, vingt événements maximum, fenêtre protocolaire de 60 secondes. La limite de réponse est un contrôle après réception, pas une garantie de téléchargement streaming borné. Identifiants distincts ; nonce avec au moins 128 bits d'entropie démontrée, sans assimiler un UUIDv4 unique à 128 bits aléatoires.

Pas de paramètre UrlFetchApp fictif timeout. RPC asynchrone après affichage du portail ; état indisponible au dépassement du budget UX, rejet des réponses tardives, double-clic maîtrisé, aucun retry automatique. Le budget UI n'annule pas le fetch serveur ; une preuve peut être écrite après abandon de l'attente par l'interface.

2. restaurer seulement les propriétés non secrètes changées par D4, dont l'absence initiale de l'URL ; préserver HMAC et version D2-B ;
3. restaurer le HEAD portail et son manifeste exactement ; retirer seulement les fichiers supplémentaires identifiés puis relire — un push réussi ne suffit pas ;
4. si autorisé et modifié, réassocier uniquement le déploiement portail cible à sa version initiale ; comparer la liste complète ; consigner les nouvelles versions immuables sans tenter de les supprimer ;
5. conserver backend version 1, déploiement et propriétés préexistantes ;
6. conserver les preuves ; ne pas effacer de clé anti-rejeu avant expiration de sa fenêtre d'acceptation ; tout nettoyage ultérieur est borné aux clés du run, sous verrou, sans suppression globale ;
7. comparer code, manifestes, propriétés par empreintes et inventaires. Toute restauration partielle est un échec.

Aucun partage ou retrait/attribution ACCESS n'est inclus. Rapports sans secret, signature, corps signé, URL backend ni contenu LOG ; références opérationnelles sensibles locales et protégées.

Après revue et fusion documentaire séparément autorisée : proposer D4-A, implémentation inactive, tests et PR applicative. Le cadrage ne résout pas encore ADMIN-006 et n'engage pas les autres modules.
