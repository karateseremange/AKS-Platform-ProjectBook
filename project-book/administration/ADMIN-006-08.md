## 1. Objet

Ce document cadre le premier raccordement réel de l’architecture privée conçue dans les lots A à C. Il définit les ressources à inventorier, les identités, les droits minimaux, le secret HMAC, le registre anti-rejeu, les preuves, la recette multi-compte et le retour arrière.

Il ne choisit, ne crée et ne modifie aucune ressource Google. Il n’autorise ni secret, ni déploiement, ni partage, ni habilitation ACCESS.

## 2. État de départ

Les éléments suivants sont intégrés dans `develop` :

- protocole signé `AKS-PRIVATE/1` ;
- commande fermée `LOG_READ_RECENT_V1` ;
- backend privé, adaptateurs et registre anti-rejeu inactifs ;
- client portail contrôlant `LOG_READ` avant tout transport ;
- widget Journaux isolé avec fonctionnement dégradé ;
- 716 tests cumulatifs réussis en RECETTE ;
- restauration exacte du HEAD RECETTE après validation.

Le portail RECETTE connu porte un identifiant Apps Script suffixé `eIRxs4`. Aucun projet backend, endpoint, secret ou support LOG n’est désigné par le présent document.

## 3. Objectif fonctionnel

Un compte secondaire disposant de `LOG_READ` doit pouvoir :

1. ouvrir le portail RECETTE sous sa propre identité ;
2. voir la destination Journaux sans acquérir de capacité `CONFIG_*` ;
3. déclencher une lecture signée côté serveur ;
4. recevoir uniquement des événements minimisés ;
5. conserver l’accès au reste du portail si le backend est indisponible.

Après retrait de `LOG_READ`, la destination doit disparaître et tout appel direct doit être refusé avant transport.

## 4. Architecture cible

| Composant | Identité d’exécution | Responsabilité |
|---|---|---|
| Portail RECETTE | utilisateur accédant | identité utilisateur, contrôle ACCESS, interface |
| Client privé du portail | contexte serveur du portail | construction et signature de la requête |
| Endpoint backend RECETTE | identité technique dédiée | validation, anti-rejeu et lecture LOG |
| Registre anti-rejeu | propriété du backend | consommation atomique des requêtes et nonces |
| Support LOG RECETTE | accès technique minimal | source des événements minimisés |
| Support de preuve | identité technique | trace minimale corrélée du traitement |

Le navigateur ne reçoit jamais l’URL privée, le secret HMAC, l’identité technique ni les identifiants Google des supports.

## 7. Identités et droits minimaux

### 7.1 Utilisateur du portail

L’adresse est résolue côté serveur par le portail. Elle n’est jamais acceptée depuis le navigateur.

L’utilisateur reçoit seulement les capacités fonctionnelles nécessaires. `LOG_READ` ne confère ni `CONFIG_READ`, ni `CONFIG_WRITE`, ni `CONFIG_RESET`, ni `ACCESS_MANAGE`.

### 7.2 Identité technique backend

L’identité technique doit :

- être distincte des comptes de test utilisateur ;
- avoir uniquement la lecture du support LOG RECETTE ;
- avoir uniquement l’écriture minimale du support de preuve retenu ;
- ne disposer d’aucun accès aux supports PRODUCTION ;
- ne pas être utilisée pour naviguer dans le portail ;
- être inventoriée avant tout partage.

### 7.3 Opérateur

L’opérateur autorisant le raccordement doit être vérifié séparément. Son rôle ne doit pas être confondu avec l’identité technique d’exécution.

## 8. Déploiement privé

Le backend doit résider dans un projet distinct du portail `USER_ACCESSING`.

Avant création d’un déploiement, le protocole doit fixer :

- l’identité d’exécution ;
- l’audience minimale techniquement viable ;
- la version exacte ;
- la description de version ;
- l’URL attendue ;
- le mécanisme d’authentification applicative HMAC ;
- l’absence de route autre que la commande fermée ;
- la procédure de suppression ou de désactivation.

Une audience réseau large ne vaut jamais autorisation fonctionnelle. Toute requête reste refusée sans signature, environnement, projet appelant, fenêtre temporelle et anti-rejeu valides.

## 9. Secret HMAC

### 9.1 Génération

Le secret doit :

- être généré par une source cryptographique ;
- contenir au moins 256 bits d’entropie ;
- ne jamais transiter dans le chat, Git, un rapport ou une cellule ;
- être installé directement dans les propriétés serveur autorisées ;
- être référencé par empreinte uniquement dans les preuves.

### 9.2 Stockage

Les propriétés logiques sont :

- `AKS_PRIVATE_HMAC_CURRENT` ;
- `AKS_PRIVATE_HMAC_PREVIOUS` pendant une rotation bornée ;
- `AKS_PRIVATE_SECRET_VERSION`.

Le portail et le backend doivent recevoir la même version courante. Toute divergence maintient Journaux indisponible sans bloquer Administration.

### 9.3 Rotation

La rotation suit quatre phases :

1. installer le nouveau secret comme courant côté backend et conserver l’ancien ;
2. installer le nouveau secret côté portail ;
3. vérifier le nouveau flux ;
4. supprimer l’ancien secret des deux côtés après la fenêtre autorisée.

Un retour arrière doit être possible tant que l’ancien secret est conservé. Les valeurs ne sont jamais affichées.

## 10. Configuration serveur

### 10.1 Portail

Les propriétés futures minimales sont :

- activation explicite ;
- environnement exact `RECETTE` ;
- URL backend ;
- projet appelant logique ;
- secret courant et version ;
- délai borné.

### 10.2 Backend

Les propriétés futures minimales sont :

- activation explicite ;
- environnement exact `RECETTE` ;
- projet appelant autorisé ;
- secrets courant et précédent ;
- identifiants des supports LOG et preuve ;
- version technique ;
- paramètres anti-rejeu bornés.

Toute propriété absente, ambiguë ou incohérente maintient le composant fermé.

## 11. Registre anti-rejeu

L’activation future utilise exclusivement les adaptateurs déjà intégrés :

- `ScriptProperties` du projet backend ;
- `ScriptLock` ;
- empreintes séparées du `requestId` et du nonce ;
- écriture atomique ;
- relecture obligatoire ;
- expiration bornée ;
- purge bornée ;
- libération du verrou dans `finally`.

Le précontrôle doit sauvegarder les propriétés préexistantes et refuser toute collision de préfixe. Le retour arrière supprime seulement les clés créées par l’opération autorisée.

## 12. Preuve technique

Chaque appel accepté produit une preuve minimisée :

- environnement ;
- commande ;
- empreinte de l’acteur ;
- identifiants de requête et de corrélation ;
- résultat ;
- durée ;
- nombre d’événements retournés ;
- version backend.

Sont interdits :

- adresse utilisateur en clair ;
- secret ou signature ;
- URL backend ;
- corps complet de requête ou réponse ;
- contenu détaillé des journaux ;
- identifiant Google inutile.

La preuve d’un refus ne doit pas révéler la cause cryptographique précise à l’appelant.

## 13. Séquence opérationnelle fermée

### D0 — inventaire

Lecture seule des projets, déploiements, propriétés par empreintes, supports et partages.

### D1 — préparation des ressources

Création ou choix explicite du backend et des supports, sous autorisation distincte. Aucun secret ni déploiement.

### D2 — installation du secret

Sauvegarde des propriétés, génération hors journal, installation croisée, vérification par empreintes. Transport encore désactivé.

### D3 — déploiement backend

Push contrôlé, relecture, tests, création de version et déploiement privé. Portail encore désactivé.

### D4 — raccordement portail

Installation de l’URL serveur, activation du client, test technique borné puis relecture.

### D5 — recette multi-compte

Attribution temporaire et séparée de `LOG_READ`, tests fonctionnels, retrait du droit et contrôle des preuves.

### D6 — clôture ou retour arrière

Conservation autorisée ou suppression des propriétés, déploiement, partages et habilitations temporaires.

Chaque sous-lot exige une autorisation explicite et un rapport avant le suivant.

## 14. Recette multi-compte

Au minimum, tester :

| Scénario | Résultat attendu |
|---|---|
| compte principal avec `LOG_READ` | Journaux disponible |
| compte secondaire avec `LOG_READ` | Journaux disponible |
| compte secondaire sans `LOG_READ` | destination absente et appel refusé avant transport |
| `LOG_READ` sans `CONFIG_*` | Journaux disponible, Paramétrage absent |
| `CONFIG_READ` sans `LOG_READ` | Paramétrage disponible, Journaux absent |
| backend désactivé | Administration disponible, widget dégradé |
| secret incohérent | Administration disponible, aucune donnée affichée |
| requête rejouée | refus anti-rejeu |
| retrait de `LOG_READ` | effet immédiat sans réutilisation d’autorisation |
| réessai | nouvelle requête et nouveau nonce |

Les comptes de test et la durée de l’habilitation temporaire doivent être approuvés avant écriture ACCESS.

## 15. Tests techniques

La validation doit inclure :

- suite cumulative complète ;
- refus avant transport ;
- projet appelant erroné ;
- environnement autre que `RECETTE` ;
- signature altérée ;
- requête expirée ;
- rejeu du `requestId` ;
- rejeu du nonce ;
- verrou indisponible ;
- support LOG indisponible ;
- preuve indisponible ;
- réponse altérée ou non corrélée ;
- rotation courant/précédent ;
- absence de fuite dans les journaux ;
- fonctionnement dégradé du portail ;
- restauration après chaque panne injectée.

## 16. Barrières de sécurité

L’opération doit s’arrêter si :

- le projet portail n’est pas exactement celui attendu ;
- une ressource contient un marqueur PRODUCTION ;
- le propriétaire ou le partage est inattendu ;
- le support LOG ou preuve n’est pas identifiable sans ambiguïté ;
- un secret existe avec une empreinte inconnue ;
- une propriété serait écrasée ;
- le backend expose une route non prévue ;
- la suite cumulative échoue ;
- la restauration ne peut pas être prouvée ;
- une habilitation temporaire ne peut pas être retirée.

## 17. Retour arrière

Le retour arrière complet suit cet ordre :

1. désactiver le client du portail ;
2. vérifier Administration en mode dégradé ;
3. retirer l’URL backend du portail ;
4. restaurer les propriétés du portail ;
5. désactiver le backend ;
6. restaurer les propriétés du backend ;
7. supprimer uniquement les clés anti-rejeu créées ;
8. retirer les partages temporaires ;
9. retirer les habilitations ACCESS temporaires ;
10. remettre le déploiement backend à son état initial ou le supprimer s’il a été créé pour la recette ;
11. relire intégralement les deux projets ;
12. vérifier les supports et preuves ;
13. archiver les rapports sans secret.

Toute restauration partielle est un échec.

Les rapports ne contiennent aucune valeur secrète, signature ou URL sensible complète.

## 19. Critères d’acceptation du cadrage

Le cadrage est recevable si :

- l’architecture sépare portail utilisateur et backend technique ;
- `LOG_READ` est contrôlé avant transport ;
- Paramétrage et Journaux restent indépendants ;
- les ressources sont inventoriées avant création ;
- le secret est installé sans exposition ;
- le registre anti-rejeu est borné et restaurable ;
- la preuve est minimisée ;
- la recette multi-compte couvre attribution et retrait ;
- le fonctionnement dégradé est testé ;
- chaque étape possède son autorisation et son retour arrière ;
- aucune opération PRODUCTION ou INSCRIPTIONS-011 n’est engagée.
