## 1. Objet

Ce document transforme la recommandation d’ADMIN-006-01 en plan d’implémentation contrôlé. Il définit un prototype limité à la lecture des journaux en RECETTE, sans implémenter le code ni créer de ressource Google.

Le prototype doit démontrer qu’un utilisateur autorisé par ACCESS peut consulter des journaux privés sans recevoir de permission directe sur leur support Google.

## 2. Périmètre fermé

Le prototype couvre exclusivement :

- la capacité `LOG_READ` ;
- une commande interne de lecture bornée ;
- le portail RECETTE existant exécuté en `USER_ACCESSING` ;
- un backend RECETTE distinct exécuté sous identité technique ;
- un support LOG RECETTE explicitement configuré ;
- une recette réelle avec un compte secondaire sans partage Drive.

Sont exclus :

- CONFIG, ACCESS, Analytics, Présences, Questionnaire santé et Calendar ;
- toute écriture métier ;
- toute modification de PRODUCTION ;
- toute migration ou suppression de journaux ;
- tout partage du classeur LOG ;
- toute modification globale du mode `executeAs` ;
- INSCRIPTIONS-011 et les futurs modules privés.

## 3. Décision d’architecture

### 3.1 Composants

| Composant | Mode d’exécution | Responsabilité |
|---|---|---|
| Portail RECETTE | `USER_ACCESSING` | identifier l’utilisateur, contrôler ACCESS, construire et signer la requête serveur |
| Backend LOG RECETTE | identité technique propriétaire | vérifier la requête, appliquer la commande autorisée, ouvrir le support LOG et minimiser la réponse |
| Support LOG RECETTE | privé | conserver les journaux ordinaires de recette |
| AUDIT RECETTE | mécanisme existant ou preuve technique dédiée selon l’étape | tracer les décisions de sécurité sans exposer le contenu des journaux |

Le navigateur n’appelle jamais directement le backend et ne reçoit aucun secret.

### 3.2 Séparation des environnements

RECETTE et PRODUCTION doivent disposer de valeurs distinctes pour :

- URL ou identifiant logique du backend ;
- secret HMAC ;
- identifiant du projet appelant ;
- identifiant du support LOG ;
- préfixe des requêtes et des nonces ;
- journaux techniques et preuves AUDIT.

Un backend RECETTE doit refuser toute enveloppe marquée PRODUCTION, et inversement.

## 4. Identités et autorités

| Identité | Source | Usage |
|---|---|---|
| Utilisateur actif | `Session.getActiveUser().getEmail()` côté portail | authentification initiale |
| Acteur fonctionnel | valeur normalisée dérivée côté serveur de l’utilisateur actif | contrôle ACCESS et preuve |
| Exécuteur technique | compte propriétaire du backend | ouverture du support privé |
| Propriétaire du support | configuration du backend | gouvernance de la ressource |

L’acteur ne doit jamais provenir d’un champ libre du navigateur. Une identité vide, non normalisable ou différente du sujet contrôlé par ACCESS entraîne un refus fermé.

## 5. Catalogue initial des commandes

Une seule commande est admise :

`LOG_READ_RECENT_V1`

Paramètres autorisés :

| Champ | Type | Règle |
|---|---|---|
| `limit` | entier | de 1 à 20 ; valeur par défaut 5 |
| `severity` | chaîne optionnelle | valeur appartenant à une liste fermée |
| `cursor` | chaîne optionnelle | opaque, bornée et validée par le backend |

Sont interdits dans la requête : identifiant de classeur, nom de feuille, URL Drive, expression de filtre libre et adresse d’un autre acteur.

## 6. Enveloppe signée

### 6.1 Requête

```json
{
  "protocol": "AKS-PRIVATE/1",
  "environment": "RECETTE",
  "callerProject": "AKS-PORTAL-RECETTE",
  "command": "LOG_READ_RECENT_V1",
  "actor": "utilisateur@example.com",
  "requestId": "uuid",
  "correlationId": "uuid",
  "issuedAt": "2026-08-28T12:00:00.000Z",
  "expiresAt": "2026-08-28T12:01:00.000Z",
  "nonce": "valeur-aleatoire",
  "payloadHash": "SHA-256-hex",
  "payload": {
    "limit": 5
  },
  "signature": "HMAC-SHA256-base64"
}
```

### 6.2 Canonicalisation

La signature porte sur une représentation canonique indépendante de l’ordre JSON :

1. version du protocole ;
2. environnement ;
3. projet appelant ;
4. commande ;
5. acteur normalisé ;
6. identifiant de requête ;
7. identifiant de corrélation ;
8. dates ISO UTC ;
9. nonce ;
10. empreinte SHA-256 du payload canonique.

Les champs sont assemblés avec une règle unique, versionnée et couverte par des vecteurs de test. La signature est vérifiée en temps constant.

### 6.3 Réponse

La réponse contient au minimum :

- `protocol` ;
- `environment` ;
- `requestId` et `correlationId` ;
- `status` ;
- données minimisées ou code d’erreur ;
- horodatage du backend ;
- signature de réponse.

La réponse ne divulgue ni secret, ni identifiant complet de support, ni trace technique interne.

## 7. Secret et rotation

Pour le prototype :

- un secret aléatoire fort est généré séparément pour RECETTE ;
- il est stocké uniquement dans les Script Properties des deux projets concernés ;
- il n’est jamais inscrit dans Git, le Project Book, les journaux ou le navigateur ;
- sa présence est vérifiée sans afficher sa valeur ;
- la rotation accepte au plus une courte période avec secret courant et secret précédent ;
- la suppression du secret côté portail désactive immédiatement le raccordement ;
- la suppression du secret côté backend fait échouer toute nouvelle requête.

La création et l’installation du secret nécessiteront une autorisation opérationnelle distincte.

## 8. Anti-rejeu et bornes temporelles

Valeurs proposées pour le prototype :

- durée maximale d’une requête : 60 secondes ;
- tolérance d’horloge : 30 secondes ;
- nonce aléatoire d’au moins 128 bits ;
- consommation atomique du nonce avant l’accès au support ;
- conservation du nonce au moins jusqu’à l’expiration augmentée de la tolérance ;
- refus d’un `requestId` ou d’un nonce déjà vu ;
- taille maximale du corps : 16 Kio ;
- limite de 20 lignes retournées.

Le stockage anti-rejeu doit être partagé par toutes les exécutions du backend RECETTE. `CacheService` seul ne constitue pas une garantie suffisante ; le prototype doit combiner verrouillage et stockage persistant borné, ou documenter une solution équivalente testable.

## 9. Ordre des contrôles backend

Le backend applique cet ordre fermé :

1. taille et syntaxe JSON ;
2. protocole, environnement et projet appelant ;
3. présence et format des champs obligatoires ;
4. dates, expiration et fenêtre d’horloge ;
5. empreinte du payload ;
6. signature en temps constant ;
7. unicité du nonce et du `requestId` ;
8. commande dans la liste blanche ;
9. schéma et bornes du payload ;
10. ouverture du support configuré ;
11. lecture bornée et minimisation ;
12. preuve technique corrélée ;
13. signature de la réponse.

Aucun accès au support privé ne doit précéder la validation complète de la requête.

## 10. Défense en profondeur côté portail

Avant l’appel au backend, le portail doit :

1. résoudre l’utilisateur actif ;
2. normaliser l’adresse ;
3. vérifier que le compte est actif ;
4. exiger explicitement `LOG_READ` ;
5. construire l’enveloppe exclusivement côté serveur ;
6. utiliser une URL backend configurée, jamais fournie par le client ;
7. appliquer un délai d’appel borné ;
8. vérifier la réponse et sa corrélation ;
9. traduire l’échec en état local contrôlé.

Le retrait de `LOG_READ` doit bloquer l’appel avant toute communication avec le backend.

## 11. Résilience du portail Administration

L’indisponibilité du backend LOG ne doit plus faire tomber `?app=admin`.

Le chargement du portail doit distinguer :

- navigation autorisée ;
- widget de journaux disponible ;
- widget temporairement indisponible.

En cas d’échec LOG :

- la carte Administration reste affichée ;
- les autres modules restent accessibles ;
- aucun détail technique sensible n’est présenté ;
- l’utilisateur peut réessayer ;
- une corrélation technique est conservée.

Ce comportement doit être validé même avant l’activation du backend, au moyen d’un adaptateur désactivé ou simulé.

## 12. Modèle d’erreurs

| Code public | Sens |
|---|---|
| `PRIVATE_AUTH_REQUIRED` | identité active absente |
| `PRIVATE_ACCESS_DENIED` | capacité ACCESS absente |
| `PRIVATE_REQUEST_INVALID` | enveloppe ou payload invalide |
| `PRIVATE_REQUEST_EXPIRED` | fenêtre temporelle dépassée |
| `PRIVATE_REPLAY_REJECTED` | nonce ou requête déjà consommé |
| `PRIVATE_BACKEND_UNAVAILABLE` | backend indisponible ou réponse inexploitable |
| `PRIVATE_OPERATION_FAILED` | échec interne générique |

Les erreurs de signature, de projet, de support ou de configuration restent indistinguables côté client afin de réduire les informations offertes à un attaquant.

## 13. Observabilité et preuves

Chaque tentative produit un événement technique minimal :

- environnement ;
- commande ;
- acteur normalisé ou empreinte contrôlée selon la politique ;
- `requestId` et `correlationId` ;
- décision autorisée/refusée ;
- code de résultat ;
- durée ;
- nombre de lignes retournées ;
- identité logique de l’exécuteur ;
- aucune valeur de secret ;
- aucun contenu de journal métier dans la preuve technique.

Le prototype en lecture seule ne doit pas transformer chaque consultation en écriture dans le support LOG consulté, afin d’éviter récursion et bruit.

## 14. Plan d’implémentation futur

### Lot A — contrats purs

- modèles de requête et réponse ;
- canonicalisation et HMAC ;
- validation des dates, tailles et payloads ;
- codes d’erreur ;
- tests unitaires et vecteurs cryptographiques.

### Lot B — backend RECETTE

- catalogue fermé de commandes ;
- vérification anti-rejeu ;
- adaptateur du support LOG RECETTE ;
- minimisation et signature de réponse ;
- preuves techniques.

### Lot C — portail RECETTE

- contrôle `LOG_READ` avant appel ;
- client serveur-à-serveur ;
- vérification de réponse ;
- isolation du widget LOG ;
- comportement dégradé sans chute du portail.

### Lot D — recette réelle

- installation séparée des propriétés RECETTE ;
- attribution temporaire et contrôlée de `LOG_READ` ;
- essais avec compte secondaire ;
- retrait et restauration exacte ;
- rapport de recette.

Chaque lot devra faire l’objet d’une autorisation, d’une branche applicative et d’une PR séparée ou d’un découpage explicitement approuvé.

## 15. Stratégie de tests

### 15.1 Tests unitaires

- canonicalisation stable ;
- signatures valides et invalides ;
- comparaison en temps constant encapsulée ;
- expiration aux limites ;
- nonce unique puis rejoué ;
- payload altéré ;
- acteur, commande, environnement et projet altérés ;
- dépassement des tailles et limites ;
- commande inconnue ;
- réponse corrélée et signée.

### 15.2 Tests d’intégration RECETTE

- support LOG accessible uniquement à l’identité technique ;
- compte secondaire sans partage Drive ;
- lecture de 1, 5 et 20 lignes ;
- filtre autorisé ;
- backend indisponible ;
- secret absent ou incorrect ;
- double envoi concurrent du même nonce ;
- retrait de `LOG_READ` immédiatement effectif.

### 15.3 Recette utilisateur

1. sauvegarder les propriétés, habilitations et supports RECETTE ;
2. confirmer l’absence de partage du support au compte secondaire ;
3. vérifier le portail sans `LOG_READ` ;
4. attribuer `LOG_READ` seul ;
5. vérifier le portail et la lecture bornée ;
6. vérifier qu’aucun autre module privé n’est accordé ;
7. couper le backend et confirmer que le portail reste utilisable ;
8. rejouer et altérer des requêtes de test ;
9. retirer `LOG_READ` ;
10. confirmer le refus immédiat ;
11. restaurer exactement l’état initial ;
12. archiver le rapport et ses empreintes.

## 16. Retour arrière

Le retour arrière du prototype doit être possible sans modifier les données LOG :

1. désactiver la propriété de raccordement côté portail ;
2. vérifier le fonctionnement du portail sans widget LOG distant ;
3. retirer l’habilitation temporaire ;
4. retirer les secrets et paramètres temporaires ;
5. restaurer les propriétés et l’état ACCESS sauvegardés ;
6. vérifier qu’aucun partage Drive n’existe ;
7. conserver uniquement les rapports et preuves autorisés ;
8. ne supprimer une ressource créée qu’après autorisation dédiée.

Aucune bascule de PRODUCTION ne fait partie de ce retour arrière.

## 17. Barrières avant implémentation

L’implémentation reste interdite tant que ne sont pas explicitement autorisés :

- la modification du dépôt applicatif ;
- le choix ou la création du projet backend RECETTE ;
- l’identité technique propriétaire ;
- le support exact des journaux RECETTE ;
- la génération et l’installation du secret ;
- l’attribution temporaire de `LOG_READ` ;
- toute opération sur les supports Google.

Avant chaque écriture, un précontrôle doit confirmer les identifiants exacts et produire une sauvegarde locale ou un état de référence approprié.

## 18. Critères d’acceptation du prototype

Le prototype sera recevable si :

- le compte secondaire consulte les journaux sans partage Drive ;
- ACCESS reste l’unique autorité fonctionnelle ;
- le backend n’accepte que `LOG_READ_RECENT_V1` ;
- une requête expirée, altérée ou rejouée est refusée ;
- le secret n’apparaît dans aucune sortie ;
- une panne du backend ne bloque pas le portail ;
- le retrait de `LOG_READ` est immédiatement effectif ;
- aucun autre module ni environnement n’est modifié ;
- la restauration RECETTE est exacte et documentée.
