## 4. Contrats déjà fermés

Le code impose déjà :

- protocole `AKS-PRIVATE/1` ;
- commande unique `LOG_READ_RECENT_V1` ;
- corps maximal de 16 384 octets ;
- fenêtre de requête maximale de 60 secondes ;
- tolérance d’horloge de 30 secondes ;
- limite de 1 à 20 événements ;
- environnement exact `RECETTE` ;
- projet appelant exact ;
- validation HMAC avant lecture LOG ;
- consommation anti-rejeu du `requestId` et du nonce ;
- preuve technique obligatoire après traitement ;
- réponses et événements minimisés ;
- refus fermé lorsque la configuration ou un port est indisponible.

Ces contrats ne suffisent pas à rendre le backend déployable.

## 5. Écarts bloquants

### 5.1 Aucun endpoint HTTP

Aucune fonction `doPost(e)` n’est exportée. Le backend ne peut recevoir aucune requête Web App.

L’endpoint D3-A devra :

1. accepter uniquement POST ;
2. extraire exclusivement `e.postData.contents` ;
3. refuser les requêtes sans corps ;
4. appeler l’orchestrateur privé ;
5. produire un JSON minimal ;
6. transformer toute erreur en réponse générique sans détail cryptographique ;
7. ne jamais journaliser le corps, la signature, le secret ou l’URL ;
8. n’exposer aucune autre commande.

### 5.2 Configuration réelle absente

L’adaptateur de configuration actuel reçoit un objet injecté. Il ne lit pas les propriétés Apps Script.

D3-A doit ajouter un adaptateur fermé lisant uniquement les clés contractuelles. Le secret courant et sa version sont déjà présents. Les clés non secrètes doivent être définies et contrôlées avant activation :

- activation explicite ;
- environnement `RECETTE` ;
- projet appelant exact ;
- identifiant du support LOG ;
- version backend ;
- paramètres anti-rejeu bornés ;
- identifiant du support de preuve.

Aucune clé ne doit utiliser une valeur par défaut permissive.

### 5.3 Lecteur LOG incompatible

`LogEventRepository` utilise par défaut `SpreadsheetApp.getActiveSpreadsheet()`. Un projet Apps Script autonome n’a pas de classeur actif.

Le backend doit ouvrir explicitement le support D1 par ID, vérifier :

- ID exact ;
- onglet exact `AKS_Logs` ;
- seize en-têtes exacts ;
- environnement RECETTE ;
- lecture seule ;
- limite stricte ;
- absence de retour des colonnes ou identifiants non autorisés.

Le support ne doit jamais être partagé aux comptes utilisateurs du portail.

### 5.4 Adaptateur de preuve absent

L’orchestrateur exige `proofWriter.write`, mais aucun support de preuve réel n’est raccordé.

Le support `AKS LOG RECETTE` contient actuellement un onglet unique et un schéma LOG exact. Il ne doit pas être réutilisé implicitement pour un schéma de preuve différent.

Avant déploiement, une décision distincte doit choisir :

- un support de preuve dédié ; ou
- un nouvel onglet dédié avec schéma fermé, après autorisation explicite.

Sans support de preuve persistant et contrôlé, D3 reste bloqué.

### 5.5 Package backend absent

Le dépôt ne contient pas de racine de package backend, de `.clasp.json` backend, ni de manifeste backend dédié. Le manifeste applicatif générique contient seulement :

- fuseau `Europe/Paris` ;
- runtime V8 ;
- journalisation Stackdriver ;
- aucune bibliothèque ;
- aucun service avancé.

Le package backend doit sélectionner seulement les fichiers nécessaires. Il ne doit pas copier les 261 fichiers du portail, ses interfaces, ses tests de production ou ses routes publiques.

## 6. Identité d’exécution et audience

### 6.1 Identité observée

Le backend et le support LOG D1 appartiennent au compte `karate.seremange@gmail.com`. Aucun compte technique distinct n’a été créé.

L’option techniquement cohérente à ce stade est un déploiement exécuté en tant que propriétaire du backend. Cette identité possède le support LOG RECETTE sans partage supplémentaire.

Cette option doit être explicitement acceptée avant D3 : le propriétaire associatif ferait alors fonction d’identité technique RECETTE. Elle ne préjuge pas de l’identité de PRODUCTION.

### 6.2 Audience

Le portail `USER_ACCESSING` doit appeler le backend côté serveur avec `UrlFetchApp`. Sans jeton OAuth backend partagé aux utilisateurs, l’audience techniquement compatible est une Web App accessible sans authentification Google, protégée applicativement par :

- HMAC ;
- environnement exact ;
- projet appelant exact ;
- fenêtre temporelle ;
- identifiants uniques ;
- anti-rejeu ;
- commande unique ;
- réponse minimisée.

Une audience `ANYONE` augmente la surface réseau. Elle n’est admissible en RECETTE qu’après revue explicite, tests de refus et confirmation que l’URL ne quitte jamais le serveur du portail.

Aucune audience n’est autorisée par ce précontrôle.

- `AKS_PRIVATE_HMAC_CURRENT` ;

- `AKS_PRIVATE_HMAC_PREVIOUS` absente.

Le portail ne reçoit aucune propriété D3. L’URL et l’activation du client relèvent de D4.

## 8. Package backend D3-A

Le package minimal devra contenir :

1. protocole privé ;
2. orchestrateur backend ;
3. adaptateurs backend ;
4. garde anti-rejeu ;
5. adaptateur de configuration Apps Script ;
6. lecteur LOG dédié par ID ;
7. écrivain de preuve dédié ;
8. endpoint `doPost` fermé ;
9. manifeste V8 Europe/Paris ;
10. tests backend dédiés exécutables avant publication.

Le package doit exclure :

- `PrivatePortalLogClient.gs` ;
- les contrôleurs et interfaces du portail ;
- ACCESS côté portail ;
- les modules métier sans dépendance backend ;
- tout identifiant ou secret codé en dur ;
- tout fichier de test dans la version publiée, sauf décision explicite contraire.

## 9. Tests requis avant tout déploiement

D3-A doit ajouter des tests pour :

- configuration absente ou désactivée ;
- propriété inconnue ou valeur hors bornes ;
- projet appelant erroné ;
- environnement autre que RECETTE ;
- secret absent et clé précédente absente ;
- POST absent, vide, trop grand ou invalide ;
- méthode ou commande interdite ;
- signature, payload ou réponse altérés ;
- expiration et dérive d’horloge ;
- rejeu de `requestId` et nonce ;
- verrou indisponible ;
- support LOG absent, mauvais onglet ou mauvais schéma ;
- support de preuve indisponible ;
- fuite de données dans réponses et journaux ;
- limitation à vingt événements ;
- réponse d’erreur générique ;
- absence de route supplémentaire ;
- package backend sans dépendance portail.

La suite cumulative applicative doit rester intégralement verte. Une validation réversible dans le backend RECETTE doit précéder toute version.

## 10. Séquence D3 recommandée

### D3-A — implémentation applicative

Sur branche dédiée :

- endpoint fermé ;
- adaptateurs réels mais désactivés par défaut ;
- package backend reproductible ;
- manifeste dédié ;
- tests ;
- PR vers `develop`.

Aucune opération Google.

### D3-B — support de preuve et propriétés non secrètes

Après décision séparée :

- créer ou préparer le support de preuve RECETTE ;
- installer les propriétés non secrètes ;
- maintenir `AKS_PRIVATE_ENABLED=false` ;
- vérifier noms et empreintes ;
- aucun déploiement.

### D3-C — validation réversible du HEAD backend

- sauvegarde exacte ;
- push temporaire du package ;
- tests directs sans endpoint public ;
- relecture ;
- restauration exacte ;
- aucune version ni déploiement.

### D3-D — version et déploiement backend

Après validation :

- push du package validé ;
- relecture intégrale ;
- version Apps Script dédiée ;
- déploiement Web App avec identité et audience explicitement autorisées ;
- tests de refus et requête signée contrôlée ;
- portail toujours non raccordé ;
- retour arrière du seul déploiement backend.

Chaque sous-lot exige une autorisation séparée.

## 11. Retour arrière

Avant D3-C ou D3-D, figer :

- HEAD backend ;
- manifeste ;
- propriétés par noms et empreintes ;
- versions et déploiements ;
- support LOG et support de preuve ;
- partages ;
- empreintes des archives locales.

Le retour arrière doit :

1. maintenir ou remettre le portail non raccordé ;
2. désactiver le backend ;
3. restaurer le déploiement backend ou le supprimer s’il a été créé par D3 ;
4. restaurer le HEAD backend ;
5. supprimer seulement les propriétés non secrètes créées par D3 ;
6. conserver les deux propriétés D2-B sauf autorisation explicite de retrait ;
7. supprimer seulement les entrées anti-rejeu créées par les tests ;
8. restaurer le support de preuve ;
9. vérifier l’absence de partage utilisateur ;
10. relire tous les états.

## 12. Décision du précontrôle

D3 n’est pas exécutable avec le code actuel.

Les blocages sont cumulatifs :

- aucun `doPost` ;
- aucun adaptateur réel de configuration ;
- lecteur LOG fondé sur le classeur actif ;
- aucun écrivain ni support de preuve choisi ;
- aucun package ou manifeste backend dédié ;
- identité d’exécution non décidée formellement ;
- audience non autorisée.

La prochaine étape recommandée est D3-A, limitée à l’implémentation applicative et aux tests, sans opération Google. Le support de preuve, les propriétés non secrètes, le push, la version et le déploiement doivent rester interdits.
