## 1. Objet

Ce document détaille le lot B prévu par ADMIN-006-02 après l’intégration du lot A. Il cadre le backend RECETTE chargé de vérifier le protocole `AKS-PRIVATE/1`, de prévenir les rejeux et de lire un support LOG privé sous identité technique.

Le présent lot reste documentaire. Il ne crée ni code applicatif, projet Apps Script, déploiement, propriété, secret, support Google ou habilitation ACCESS.

## 2. Résultat attendu

Le lot B devra fournir un composant backend testable qui :

- n’accepte que la commande `LOG_READ_RECENT_V1` ;
- réutilise sans divergence les contrats purs du lot A ;
- vérifie intégralement la requête avant tout accès privé ;
- consomme atomiquement le couple requête/nonce ;
- ouvre le support LOG par une configuration serveur ;
- retourne au plus 20 événements minimisés ;
- signe et corrèle chaque réponse ;
- échoue fermé sans exposer de détail technique ;
- reste strictement limité à RECETTE.

Le raccordement du portail, le déploiement et la recette multi-compte appartiennent aux lots suivants.

## 4. Architecture logique

| Composant | Responsabilité | Dépendances autorisées |
|---|---|---|
| Point d’entrée HTTP futur | taille, méthode, décodage et réponse HTTP générique | contrôleur backend uniquement |
| Contrôleur privé | ordre des contrôles et orchestration | contrats lot A, anti-rejeu, LOG, preuve |
| Contrats lot A | canonicalisation, HMAC, validation, réponse signée | `Utilities` cryptographique |
| Registre anti-rejeu | consommation atomique et purge bornée | `LockService`, `PropertiesService` |
| Adaptateur LOG | lecture bornée du support configuré | dépôt LOG injecté |
| Adaptateur de preuve | événement technique minimal | dépôt de preuve injecté |
| Configuration serveur | environnement et identifiants logiques | Script Properties futures |

Le navigateur ne connaît ni l’URL interne, ni le secret, ni l’identifiant du support. Le backend ne fait confiance à aucun champ provenant du navigateur sans validation cryptographique.

## 5. Point d’entrée futur

Le futur endpoint devra :

1. accepter uniquement `POST` ;
2. refuser les corps absents ou supérieurs à 16 384 octets UTF-8 ;
3. limiter la réponse à du JSON ;
4. transmettre le corps brut au contrôleur ;
5. convertir toute exception non reconnue en `PRIVATE_OPERATION_FAILED` ;
6. ne jamais renvoyer de pile, nom de propriété, identifiant Google ou message interne.

L’accessibilité exacte du futur déploiement Apps Script devra être décidée et autorisée séparément. Si le point d’entrée est techniquement joignable au-delà du portail, la possession du secret HMAC, les bornes temporelles, l’anti-rejeu et le catalogue fermé constituent des contrôles obligatoires, non des options.

## 7. Stockage anti-rejeu retenu

### 7.1 Choix

Pour le prototype RECETTE, le registre utilise :

- `PropertiesService.getScriptProperties()` pour un état partagé et persistant ;
- `LockService.getScriptLock()` pour sérialiser la décision ;
- des empreintes SHA-256 des identifiants, jamais les valeurs brutes ;
- une expiration calculée à partir de `expiresAt` et de la tolérance ;
- une purge bornée à chaque consommation.

`CacheService` peut accélérer un refus, mais ne constitue jamais la source d’autorité.

### 7.2 Clés et données

Deux clés sont réservées par requête :

- `AKS_PRIVATE_REPLAY_REQ_<digest>` ;
- `AKS_PRIVATE_REPLAY_NONCE_<digest>`.

La valeur contient uniquement :

- version de schéma ;
- instant d’expiration en millisecondes ;
- corrélation technique minimale si nécessaire.

Aucun acteur, secret, payload ou contenu LOG n’est stocké dans le registre.

### 7.3 Transaction de consommation

Sous verrou exclusif :

1. acquérir le verrou avec un délai borné ;
2. relire l’horloge ;
3. purger au maximum un nombre configuré d’entrées expirées ;
4. vérifier l’absence des deux clés ;
5. écrire les deux clés par une opération groupée ;
6. relire leur présence ;
7. libérer le verrou dans un bloc `finally`.

Le jeton est consommé avant la lecture LOG. Si la lecture échoue ensuite, la requête ne redevient pas rejouable.

Tout échec de verrou, stockage, relecture ou purge critique entraîne `PRIVATE_REPLAY_REJECTED` ou `PRIVATE_BACKEND_UNAVAILABLE`, sans lecture du support.

### 7.4 Bornage

Valeurs initiales proposées :

| Paramètre | Valeur |
|---|---:|
| fenêtre de requête | 60 s |
| tolérance d’horloge | 30 s |
| attente maximale du verrou | 5 s |
| conservation minimale | expiration + tolérance |
| purge maximale par appel | 50 entrées |
| limite d’alerte du registre | à mesurer avant déploiement |

Un test de capacité devra confirmer les quotas réels du projet RECETTE avant toute installation. Le backend doit refuser fermé si l’espace ne permet plus une consommation fiable.

## 8. Configuration future

Les noms logiques suivants sont réservés, sans valeur dans Git :

| Propriété | Usage |
|---|---|
| `AKS_PRIVATE_ENVIRONMENT` | valeur exacte `RECETTE` |
| `AKS_PRIVATE_CALLER_PROJECT` | appelant autorisé |
| `AKS_PRIVATE_HMAC_CURRENT` | secret courant |
| `AKS_PRIVATE_HMAC_PREVIOUS` | ancien secret durant rotation bornée |
| `AKS_PRIVATE_LOG_RESOURCE` | identifiant serveur du support LOG |
| `AKS_PRIVATE_ENABLED` | coupe-circuit explicite |

Le backend refuse toute requête si une propriété obligatoire manque, si l’environnement diffère ou si le coupe-circuit n’est pas exactement actif. Aucune valeur réelle ne sera documentée.

## 9. Adaptateur LOG

L’adaptateur reçoit un dépôt injecté et un payload déjà validé. Il ne reçoit jamais d’identifiant de support fourni par l’appelant.

Il applique :

- limite de 1 à 20 ;
- niveaux fermés `DEBUG`, `INFO`, `WARN`, `ERROR`, `CRITICAL` ;
- curseur opaque signé ou vérifié par le backend ;
- ordre stable du plus récent au plus ancien ;
- lecture seule ;
- projection explicite des champs autorisés.

Les identifiants internes, formules, métadonnées Drive, adresses non nécessaires et contenus sensibles hors contrat sont supprimés de la réponse.

## 10. Preuve et observabilité

Une tentative authentifiée produit au maximum :

- environnement ;
- commande ;
- empreinte contrôlée de l’acteur ;
- `requestId` et `correlationId` ;
- résultat générique ;
- durée ;
- nombre d’événements retournés ;
- version logique du backend.

Sont interdits : secret, signature complète, nonce brut, payload complet, identifiant du support, contenu LOG et pile d’exception.

L’indisponibilité du mécanisme de preuve ne doit pas transformer une lecture en succès silencieux : le comportement exact sera injecté et testé, puis aligné sur AUDIT avant toute ressource réelle.

## 11. Gestion du secret et rotation

Le code futur ne contiendra aucun secret. L’installation exigera une autorisation distincte.

La rotation prévue :

1. installer le nouveau secret côté backend comme courant ;
2. conserver temporairement l’ancien comme précédent ;
3. installer le nouveau côté portail ;
4. vérifier les échanges ;
5. supprimer l’ancien des deux côtés dans une fenêtre bornée ;
6. conserver seulement les preuves non sensibles.

Le backend signe toujours avec le secret courant. L’acceptation du secret précédent doit être temporaire, mesurable et désactivable. L’absence de secret ferme le service.

## 13. Tests obligatoires

### 13.1 Contrôleur

- requête valide ;
- méthode ou JSON invalide ;
- environnement et appelant incorrects ;
- signature, payload ou acteur altérés ;
- requête expirée ou future ;
- commande inconnue ;
- réponse corrélée et signée ;
- exception interne masquée ;
- aucune lecture LOG avant validation complète.

### 13.2 Anti-rejeu

- première consommation acceptée ;
- même `requestId` refusé ;
- même nonce avec autre requête refusé ;
- deux appels concurrents : un seul accepté ;
- expiration et purge ;
- purge limitée ;
- verrou indisponible ;
- écriture ou relecture impossible ;
- saturation simulée ;
- aucune donnée sensible persistée.

### 13.3 LOG et preuve

- limites 1, 5 et 20 ;
- niveau autorisé et niveau inconnu ;
- curseur valide, altéré et trop long ;
- projection exacte des champs ;
- support absent ou indisponible ;
- preuve minimale ;
- absence de secret et contenu LOG dans les sorties techniques.

### 13.4 Non-régression

La suite cumulative Apps Script devra être recalculée depuis le tableau réel de `AKS_runValidationSuiteV11`, exécutée intégralement en RECETTE de façon réversible, puis restaurée exactement. Aucun total ne doit être déduit du simple nombre d’objets nommés dans le fichier.
