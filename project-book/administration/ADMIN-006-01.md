## 1. Objet

Ce document exécute les trois premières étapes d’ADMIN-006 :

1. inventaire des routes et des supports ;
2. matrice ACCESS / identité Apps Script / permission Google ;
3. comparaison des options d’architecture.

Il ne modifie ni le code, ni les supports Google, ni les droits, ni la production.

## 2. Règle d’exécution confirmée

La documentation officielle Apps Script distingue deux modes :

- **exécuter en tant qu’utilisateur accédant à l’application** : le script s’exécute avec l’identité et les autorisations Google de l’utilisateur actif ;
- **exécuter en tant que propriétaire** : le script utilise l’autorité du compte qui a déployé l’application.

La production utilise `USER_ACCESSING`. Une capacité ACCESS n’accorde donc aucun droit Google implicite sur un classeur, un dossier ou un fichier.

Le passage global en exécution propriétaire n’est pas neutre : `Session.getActiveUser().getEmail()` peut être vide dans une Web App exécutée comme le développeur, notamment lorsque les comptes ne relèvent pas du même domaine Workspace. AKS Platform utilisant des comptes Gmail grand public, cette identité ne peut pas être supposée disponible.

Références officielles :

- https://developers.google.com/apps-script/guides/web
- https://developers.google.com/apps-script/reference/base/session

## 3. Inventaire des mécanismes de stockage

| Mécanisme | Implémentation V1.4.1 | Effet en `USER_ACCESSING` |
|---|---|---|
| Registre ACCESS | Script Properties, clé `AKS_ACCESS_REGISTRY` | Accessible au code du projet ; aucune permission Drive directe |
| Paramètres CONFIG | Script Properties, préfixe `AKS_CONFIG_VALUE.` | Accessible au code du projet ; aucune permission Drive directe |
| Audit persistant | `SpreadsheetApp.openById` + `DriveApp.getFileById` | Exige l’accès du compte actif au classeur et au fichier |
| Journaux LOG | `SpreadsheetApp.getActiveSpreadsheet()`, feuille `AKS_Logs` | Exige l’accès du compte actif au classeur lié |
| Questionnaire santé | classeur actif ou `openById`, Drive, génération et courriel | Exige les autorisations Google du compte actif |
| Sources Analytics | cinq `SpreadsheetApp.openById` configurés | Exige l’accès en lecture du compte actif aux cinq classeurs |
| Présences | classeurs de cours par `openById` | Exige lecture ou écriture selon l’action |
| Publication Analytics | `DriveApp.getFolderById`, création de dossiers et fichiers | Exige les droits Drive du compte actif |
| Verrous et caches | LockService, CacheService | Ressources techniques du script, sans partage Drive |
| Calendar | aucune utilisation active trouvée dans V1.4.1 | À inventorier avant raccordement futur |

## 4. Matrice des routes

| Route | Capacités principales | Chargement initial | Actions ultérieures | Risque multi-compte |
|---|---|---|---|---|
| `?app=admin` | projection de toutes les capacités | registre ACCESS ; si `LOG_READ`, lecture des journaux récents | navigation | **Bloquant** : une dépendance LOG peut faire tomber le portail |
| `?app=config` | `CONFIG_READ`, `CONFIG_WRITE`, `CONFIG_RESET` | registre ACCESS et Script Properties | écriture CONFIG + preuve AUDIT | lecture probablement autonome ; écriture bloquée sans accès AUDIT |
| `?app=logs` | `LOG_READ` | registre ACCESS puis `AKS_Logs` | lecture filtrée | bloqué sans accès au classeur actif |
| `?app=access` | `ACCESS_MANAGE` | registre ACCESS | mutation du registre + preuve AUDIT ; historique AUDIT | consultation possible ; mutation ou historique dépend du support AUDIT |
| `?app=my-access` | identité authentifiée | registre ACCESS | aucune mutation | faible : Script Properties seulement |
| `?app=analytics` | `ANALYTICS_READ`, `ANALYTICS_PREVIEW`, `ANALYTICS_PUBLISH` | registre ACCESS et paramètres | lecture de cinq classeurs ; publication Drive | la page peut s’ouvrir alors que les opérations échouent |
| `?app=attendance` | capacités cours et présence | registre ACCESS, paramètres et classeurs de cours | lecture/écriture Sheets | dépend des partages de chaque classeur |
| `?app=attendance-recipe` | route de recette | ressources de recette | écritures de recette | ne doit pas devenir une dépendance de production |
| URL sans `app` | contrat public Questionnaire santé | installation du module et classeur Questionnaire | Drive, courriels et écritures Sheets | dépend des autorisations du visiteur dans le mode actuel |
| `doPost` | signature du connecteur WordPress | paramètres techniques | Questionnaire, Drive et courriel | identité et autorisations du contexte d’appel à confirmer |

## 5. Lecture de l’incident V1.4.1

L’habilitation testée comportait simultanément :

- `CONFIG_READ` ;
- `CONFIG_WRITE` ;
- `CONFIG_RESET` ;
- `LOG_READ`.

Le retrait complet a restauré le portail. Le code permet d’identifier `LOG_READ` comme premier déclencheur probable :

1. `AccessPortalProjectionService` ajoute `admin.logs` ;
2. `AdminDashboardController` tente de charger les cinq journaux récents ;
3. `AdminLogController` interroge `AKS.LogEventRepository` ;
4. `LogEventRepository` ouvre le classeur actif.

Le contrôle en production n’a pas isolé chaque capacité. La causalité unitaire de `LOG_READ` reste donc à confirmer en RECETTE, jamais par une nouvelle attribution directe en production.

## 6. Écarts entre tests antérieurs et réalité

Les validations unitaires utilisent principalement des dépôts injectés ou en mémoire. Elles démontrent les règles ACCESS, mais pas les permissions Google réelles.

La recette doit être considérée insuffisante si le compte secondaire :

- possède déjà un accès Drive aux supports ;
- utilise le même compte que le propriétaire ;
- ne déclenche que le rendu de la page, sans exécuter les opérations ;
- ne couvre pas chaque capacité séparément ;
- ne vérifie pas l’absence de partage direct après succès.

Le contrôle « Analytics : OK » réalisé après publication prouve uniquement le chargement de sa page. Il ne démontre pas que les cinq classeurs peuvent être diagnostiqués ni que les rapports peuvent être publiés.

## 7. Invariants de sécurité affinés

La solution cible doit distinguer quatre identités :

| Identité | Rôle |
|---|---|
| Utilisateur actif | personne connectée et autorisée par ACCESS |
| Acteur fonctionnel | identité portée dans l’action et la preuve AUDIT |
| Exécuteur technique | identité autorisée à ouvrir le support privé |
| Propriétaire du support | compte responsable de la ressource Google |

Une action n’est conforme que si :

- l’utilisateur actif est identifié côté serveur ;
- ACCESS autorise exactement la capacité ;
- l’acteur fonctionnel est lié à cette identité sans valeur fournie librement par le navigateur ;
- l’exécuteur technique n’élargit pas les droits fonctionnels ;
- la ressource privée reste non partagée ;
- l’audit enregistre l’acteur et le contexte technique ;
- une requête ne peut pas être rejouée ou détournée vers une autre opération.

## 8. Comparaison des options

Échelle : 1 = défavorable, 5 = favorable.

| Option | Confidentialité | Identité acteur | Isolation | Évolutivité | Complexité favorable | Appréciation |
|---|---:|---:|---:|---:|---:|---|
| A. Tout exécuter comme propriétaire | 5 | 1 | 2 | 3 | 4 | Risque de perdre l’identité Gmail active et impact global |
| B. Portail utilisateur + backend privé signé | 5 | 5 | 5 | 5 | 2 | **Recommandée pour prototype** |
| C. Partager les supports aux administrateurs | 1 | 5 | 1 | 1 | 3 | Rejetée comme architecture générale |
| D. Remplacer Drive/Sheets par d’autres stockages | 4 | 5 | 4 | 3 | 1 | À réserver aux besoins justifiés, pas au correctif initial |

## 9. Option B — architecture recommandée pour prototype

### 9.1 Principe

- Le portail public/privé actuel reste exécuté en `USER_ACCESSING`.
- Il identifie l’utilisateur par `Session.getActiveUser()`.
- Il contrôle ACCESS avant tout appel.
- Les opérations nécessitant un support privé sont envoyées à un backend distinct exécuté sous identité technique.
- Le backend n’est pas une seconde interface utilisateur.
- Il n’accepte qu’un catalogue fermé de commandes internes.

### 9.2 Enveloppe de requête minimale

Une requête interne devrait porter :

- version de protocole ;
- commande autorisée ;
- acteur normalisé ;
- identifiant de requête ;
- corrélation ;
- horodatage ;
- expiration courte ;
- nonce anti-rejeu ;
- empreinte du payload ;
- environnement exact ;
- identifiant logique du projet appelant ;
- signature HMAC.

Le navigateur ne doit jamais recevoir le secret ni fabriquer l’identité signée.

### 9.3 Contrôles backend

Le backend doit :

1. vérifier l’environnement et le projet appelant ;
2. vérifier la signature en temps constant ;
3. refuser toute commande inconnue ;
4. vérifier l’expiration et le nonce ;
5. appliquer une limite de taille ;
6. revalider le schéma de la commande ;
7. ouvrir uniquement le support prévu ;
8. produire une preuve AUDIT corrélée ;
9. retourner une réponse minimisée et signée ;
10. ne jamais retourner un identifiant complet ou une donnée sensible inutile.

### 9.4 Limitation du prototype

Le premier prototype doit couvrir un chemin en lecture seule, de préférence la consultation bornée des journaux. Il ne doit pas commencer par une écriture CONFIG ou ACCESS.

Le prototype ne doit pas :

- modifier le déploiement de production ;
- partager un support ;
- migrer les journaux ;
- exposer un secret au client ;
- accepter une URL ou un identifiant de classeur fourni par l’appelant ;
- réutiliser le backend de RECETTE en PRODUCTION.

## 10. Décisions encore nécessaires

Avant implémentation, le Product Owner doit valider :

- la séparation en deux projets ou deux déploiements Apps Script ;
- le propriétaire et l’identité technique ;
- le catalogue initial des commandes ;
- la gestion et la rotation du secret ;
- la durée de validité et la stratégie anti-rejeu ;
- le support des journaux ordinaires ;
- l’ordre de migration des routes ;
- la stratégie de retour arrière ;
- l’impact sur le lien public Questionnaire santé.

## 11. Recette ADMIN-006-01

Le compte secondaire ne doit recevoir aucun partage Drive direct.

Séquence minimale :

1. confirmer l’absence de permissions sur le support LOG ;
2. attribuer `LOG_READ` seul en RECETTE ;
3. charger le portail ;
4. consulter les journaux via le prototype ;
5. retirer `LOG_READ` ;
6. vérifier le refus immédiat ;
7. rejouer une requête signée et obtenir un refus ;
8. altérer l’acteur, la commande, l’environnement et la signature ;
9. simuler l’indisponibilité du backend sans chute du portail ;
10. restaurer exactement ACCESS, AUDIT, propriétés et supports de RECETTE.

Une deuxième campagne couvrira ensuite `CONFIG_READ`, puis les écritures CONFIG avec audit persistant.

## 12. Recommandation

Retenir l’option B comme base d’un prototype de lecture LOG en RECETTE, sous réserve d’une décision d’architecture explicite.

Ne pas modifier globalement `executeAs`, ne pas partager les supports sensibles et ne pas engager les futurs modules privés avant validation du prototype et de la recette multi-compte.
